Lecture 39: Introduction to RMI (Remote Method Invocation)

1. What is RMI?

Technical Definition: Remote Method Invocation (RMI) is a Java API that allows an object running in one Java Virtual Machine (JVM) to invoke methods on an object running in another JVM (even on a different physical computer over a network).

Why is it used? It is the foundation for creating Distributed Applications in Java. Instead of writing complex, low-level Socket code (like we did in Lecture 21) where you have to manually parse bytes, RMI allows you to call a remote method exactly as if it were a local method.

Roman Urdu Explanation: Normal Java mein, ek object sirf usi computer ki RAM (JVM) mein maujood doosre objects ke functions call kar sakta hai. Lekin agar aap chahein ke Lahore mein baithe ek computer (Client) ka program, Karachi mein chalte hue Server ke kisi method/function ko call kare aur result wapas laye, tou uske liye RMI use hota hai. RMI background mein sockets khud handle karta hai, aapko lagta hai jaise function aapke apne hi computer par chal raha ho.

2. The RMI Architecture (Stubs & Skeletons)

RMI hides the network complexity using two proxy objects:

  • Stub (Client-side proxy): It acts as a gateway for the client. The client calls a method on the Stub. The Stub converts the parameters into bytes (Serialization), sends them over the network, waits for the result, and returns it to the client.
  • Skeleton (Server-side proxy): It listens on the server side. It receives the bytes from the Stub, converts them back to data (Deserialization), calls the actual function on the server, and sends the result back to the Stub.

3. RMI Registry

Technical Definition: The RMI Registry is a simple directory service. The Server registers its remote objects here, giving them unique names (like a phonebook). The Client looks up the RMI registry using a name to get a reference to the Stub.

Quick Revision - Lecture 39

  • RMI: Remote Method Invocation. Used for distributed computing.
  • Stub: Client-side proxy object. Marshals (serializes) parameters.
  • Skeleton: Server-side proxy object. Unmarshals parameters and invokes the real method.
  • Registry: The phonebook where server objects are stored by name.

Lecture 40: RMI Architecture & Code Implementation

1. Steps to Create an RMI Application

Creating an RMI application strictly follows these 5 steps:

  1. Create a Remote Interface.
  2. Provide the Implementation for that interface.
  3. Create the Server application to host the object.
  4. Create the Client application to call the object.
  5. Generate Stubs and Skeletons using the rmic tool.

2. RMI Code Example (Step-by-Step)

Step 1: The Remote Interface

Must extend java.rmi.Remote and every method must throw RemoteException.

import java.rmi.*;

// 1. Interface must extend Remote
public interface Calculator extends Remote {
    // 2. All methods must throw RemoteException
    public int add(int a, int b) throws RemoteException;
}

Step 2: The Implementation Class

Must extend UnicastRemoteObject so it can be exported to the network.

import java.rmi.server.*;
import java.rmi.*;

// 1. Extend UnicastRemoteObject and implement our interface
public class CalculatorImpl extends UnicastRemoteObject implements Calculator {
    
    // 2. Default constructor throwing RemoteException is mandatory
    public CalculatorImpl() throws RemoteException {
        super();
    }
    
    // 3. The actual business logic
    public int add(int a, int b) throws RemoteException {
        return a + b;
    }
}

Step 3: The Server

import java.rmi.*;

public class RMIServer {
    public static void main(String args[]) {
        try {
            // 1. Create the remote object
            Calculator stub = new CalculatorImpl();
            
            // 2. Bind (register) it in the RMI Registry with a unique name
            Naming.rebind("rmi://localhost:1099/MyCalc", stub);
            
            System.out.println("Server is Ready!");
        } catch(Exception e) { System.out.println(e); }
    }
}

Step 4: The Client

import java.rmi.*;

public class RMIClient {
    public static void main(String args[]) {
        try {
            // 1. Lookup the object in the registry using the exact name
            Calculator remoteObj = (Calculator) Naming.lookup("rmi://localhost:1099/MyCalc");
            
            // 2. Call the method as if it's running locally!
            int result = remoteObj.add(10, 20);
            System.out.println("Result from server: " + result);
            
        } catch(Exception e) { System.out.println(e); }
    }
}
Important Rule (rmic tool): After compiling your .java files into .class files, you MUST run a special command in the terminal/command prompt: rmic CalculatorImpl. This generates the internal Stub and Skeleton files required by RMI. (Note: In newer Java versions this is automated, but it is a core exam point in CS506).

Quick Revision - Lecture 40

  • java.rmi.Remote: Interface required for remote methods.
  • RemoteException: Must be thrown by all remote methods to handle network failures.
  • UnicastRemoteObject: Class used to export the object to the RMI runtime.
  • Naming.rebind(): Used by server to register the object.
  • Naming.lookup(): Used by client to find the object.

Lecture 41: Introduction to EJB (Enterprise JavaBeans)

1. What is EJB?

Technical Definition: Enterprise JavaBeans (EJB) is a server-side component architecture for Java Enterprise Edition (Java EE). It encapsulates the business logic of an application and runs inside a special environment called an EJB Container (like JBoss or GlassFish).

Roman Urdu Explanation: Jab aap koi bohat bada software banate hain (jaise Bank ka system), tou sirf business logic likhna kafi nahi hota. Aapko Security, Database Transactions, Multiple users ka load (Concurrency), aur network connection bhi khud code karna parta hai. EJB yeh saari extra tension khatam kar deta hai. EJB ka "Container" security aur memory khud handle karta hai, developer sirf business rules (e.g. account se paise minus karna) likhne par focus karta hai.

2. Standard JavaBeans vs Enterprise JavaBeans (EJB)

This is a crucial comparison for exams.

Standard JavaBean (Lecture 33) Enterprise JavaBean (EJB)
Runs in a standard JVM (client or basic server). Requires an Enterprise Server/EJB Container (e.g., GlassFish).
Used as a simple Data Structure (Model) to carry data. Used to write heavy Business Logic and Distributed systems.
Developer handles thread safety and transactions. Container automatically manages transactions and concurrency.
Does not support Remote network calls by default. Built specifically to be called remotely (RMI is used internally).

3. Types of Enterprise Beans

  • Session Beans: Perform tasks for a client (business logic). Can be Stateful or Stateless.
  • Entity Beans: Represent persistent data stored in a database (like a row in a table). (Note: Largely replaced by JPA in modern Java, but heavily tested in CS506).
  • Message-Driven Beans: Used for asynchronous communication (background processing without making the user wait).

Quick Revision - Lecture 41

  • EJB: Server-side architecture for enterprise business logic.
  • Container: The environment that runs EJBs and provides system-level services (security, transactions).
  • Separation of Logic: Developers write logic; Container handles middleware services.
  • Three Types: Session, Entity, and Message-Driven Beans.

Lecture 42: EJB Architecture & Session Beans

1. EJB Component Architecture (EJB 2.x Model)

Writing an EJB is more complex than a standard class. In the classic EJB model taught in CS506, one EJB component requires three different files:

  1. Remote Interface: Contains the business methods that the client can call (e.g., depositMoney()).
  2. Home Interface: Contains lifecycle methods. Used by the client to create(), find, or remove the EJB object.
  3. Bean Class: The actual Java code that implements the logic.
Roman Urdu Explanation: Client seedha EJB ki class (Bean) ko haath nahi laga sakta. Agar client ko EJB use karni hai, tou wo pehle Home Interface se kehta hai "Mujhe ek EJB create kar ke do". Jab EJB ban jati hai, tou client uske functions ko Remote Interface ke zariye call karta hai. Yeh strict rules isliye hain taake EJB Container in calls ke darmayan apni security aur transactions apply kar sake.

2. Deep Dive: Session Beans

Session beans execute tasks for a specific client. They are divided into two main categories:

A. Stateless Session Beans

Definition: A bean that does NOT maintain a conversational state with the client. When a client calls a method, the bean executes it and forgets everything about the client immediately after.

Use Case: Credit card verification, converting Fahrenheit to Celsius, Calculator. (Tasks that only depend on the input parameters of that specific method).

Advantage: Highly scalable. The server can use a pool of 10 beans to serve 100 clients, picking a random bean for every request.

B. Stateful Session Beans

Definition: A bean that maintains a conversational state (memory) with a specific client across multiple method calls. The container assigns a unique bean instance to a specific client.

Use Case: Shopping Cart (where adding Item 1 and Item 2 across different clicks must be remembered by the server).

Disadvantage: Consumes more RAM. The server must keep the bean alive as long as the client is active.

Important Rules / Exam Tips:
  • Lifecycle difference: Stateless beans only have two states: Does Not Exist and Method-Ready. Stateful beans have three: Does Not Exist, Method-Ready, and Passivated (Sleeping in hard drive to save RAM).
  • EJB uses RMI internally: You don't have to write Stub and Skeleton code manually in EJB; the EJB container handles the RMI network communication for you automatically.

Quick Revision - Lecture 42

  • Home Interface: Used for creating/finding beans.
  • Remote Interface: Used for executing business logic.
  • Stateless Bean: No memory of past requests. Fast, scalable. (e.g., Calculator).
  • Stateful Bean: Remembers past requests for a specific client. Uses more memory. (e.g., Shopping Cart).

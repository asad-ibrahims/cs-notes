Lecture 43: Entity Beans & Message-Driven Beans (MDB)

1. What are Entity Beans?

Technical Definition: While Session Beans contain business logic, Entity Beans represent persistent data stored in a relational database. An Entity Bean object typically corresponds to a single row in a database table (e.g., a `StudentBean` represents one student row in the `Students` table).

Roman Urdu Explanation: Session beans calculations ya tasks karte hain. Lekin agar humein database mein data save ya read karna ho, tou hum Entity Beans use karte hain. Ek Entity Bean ka object bilkul database ki ek row jaisa hota hai. EJB container is data ko zinda (persistent) rakhta hai. Agar server crash bhi ho jaye, tou DB mein data mehfooz rehta hai.

2. Two Types of Entity Beans (CMP vs BMP)

This is a major exam topic in CS506. How does the Bean actually talk to the database?

CMP (Container-Managed Persistence) BMP (Bean-Managed Persistence)
The EJB Container writes and executes all SQL queries automatically. The Developer must write all JDBC (SQL) code manually inside the bean.
Developer only writes abstract getter/setter methods. Developer writes `INSERT`, `UPDATE`, `DELETE` statements.
Fast to develop, easy to switch databases. Slower to develop, harder to switch databases.
Less control over complex queries. Full control over complex database operations.

3. Message-Driven Beans (MDB)

Technical Definition: A Message-Driven Bean is an enterprise bean that allows Java applications to process messages asynchronously. It uses JMS (Java Message Service).

Roman Urdu Explanation: Normal EJB mein, client request bhejta hai aur jawab ka wait karta hai (Synchronous). Lekin kuch kaam aisay hote hain jinme wait nahi karwana chahiye, jaise email send karna. MDB ek aisi EJB hai jisko client direct call nahi karta. Client sirf ek "Message" queue mein daal kar apna kaam karta rehta hai. MDB background mein us message ko uthata hai aur process karta hai (Asynchronous). Iska koi return type nahi hota. 
import javax.ejb.MessageDrivenBean;
import javax.jms.Message;
import javax.jms.MessageListener;

public class MyEmailMDB implements MessageDrivenBean, MessageListener {
    
    // This is the ONLY method used to process incoming messages!
    public void onMessage(Message msg) {
        // Read message and send email in the background
        System.out.println("Processing async message...");
    }
    
    // (Lifecycle methods omitted for brevity)
}
Important Rule for MDBs: MDBs do NOT have a Home Interface or Remote Interface. Clients never connect to them directly. They only have the bean class and the `onMessage()` method.

Quick Revision - Lecture 43

  • Entity Bean: Represents persistent DB data (a row in a table).
  • BMP: Developer writes the SQL.
  • CMP: Server/Container writes the SQL.
  • MDB: Used for asynchronous background processing (JMS). No client interfaces.

Lecture 44: Introduction to Web Services

1. The Problem with RMI & EJB (Why Web Services?)

We learned that RMI and EJB are great for distributed computing. However, they have a massive flaw: Interoperability. RMI and EJB require both the client and the server to be written in Java.

Roman Urdu Explanation: Agar mera server Java mein bana hai aur kisi doosri company ka client .NET ya PHP mein bana hai, tou RMI wahan fail ho jata hai kyunke RMI sirf Java ki zubaan samajhta hai. Is maslay ko hal karne ke liye Web Services banayi gayin. Web services internet (HTTP) aur XML ka istemaal karti hain, jisse koi bhi language kisi doosri language se baat kar sakti hai.

2. What is a Web Service?

Technical Definition: A Web Service is any piece of software that makes itself available over the internet and uses a standardized XML messaging system (SOAP). It allows communication between different applications running on different platforms and frameworks.

  • Platform Independent: A Windows client can consume a Linux web service.
  • Language Independent: A Python app can consume a Java web service.
  • Loosely Coupled: The client doesn't need to know how the server is coded.

3. Core Technologies of Web Services

Web services rely on three fundamental standards (often asked in exams):

  1. SOAP (Simple Object Access Protocol): The format of the message sent across the network. (XML based).
  2. WSDL (Web Services Description Language): A document that describes what the service does and how to connect to it.
  3. UDDI (Universal Description, Discovery, and Integration): A registry (directory) where web services can be listed and found.

4. SOAP Structure

A SOAP message is simply an XML document wrapped in an "Envelope". It acts like a digital postal letter.

<?xml version="1.0"?>
<!-- 1. The Envelope wraps the whole message -->
<soap:Envelope>

    <!-- 2. Header: Contains metadata, authentication, routing -->
    <soap:Header>
        <authKey>12345</authKey>
    </soap:Header>
    
    <!-- 3. Body: Contains the actual data/method call -->
    <soap:Body>
        <GetWeather>
            <CityName>Lahore</CityName>
        </GetWeather>
    </soap:Body>
    
    <!-- 4. Fault: Only appears if there is an error (Optional) -->
    <!-- <soap:Fault>...</soap:Fault> -->

</soap:Envelope>

Quick Revision - Lecture 44

  • RMI Flaw: Tightly coupled, strictly Java-to-Java.
  • Web Service: Platform and language independent communication via HTTP and XML.
  • SOAP: XML protocol for sending the actual messages. Contains Envelope, Header, Body, and Fault.

Lecture 45: Web Services Architecture (Publish, Find, Bind)

1. The Service Oriented Architecture (SOA)

As per the CS506 Handouts, the architecture of Web Services relies on three distinct roles and three specific operations. This forms a triangle of communication.

The Three Roles:

  • Service Provider (Server): The company or server that writes and hosts the web service (e.g., a Weather API).
  • Service Registry (UDDI): A central directory or "Yellow Pages" on the internet where services are listed.
  • Service Requestor (Client): The application that wants to use the web service.

2. The Three Operations (Publish, Find, Bind)

How do these three roles interact? Through these three steps:

  1. PUBLISH (Provider -> Registry): The Service Provider generates a WSDL file and uploads (publishes) it to the UDDI Registry so the world knows it exists.
  2. FIND (Client -> Registry): The Service Requestor queries the UDDI Registry looking for a specific service (e.g., "Find me a weather service"). The Registry returns the WSDL file.
  3. BIND (Client -> Provider): Using the details inside the WSDL file, the Requestor connects directly to the Provider using SOAP over HTTP to execute the service.
Roman Urdu Explanation: Isko ek aam misaal se samjhein. Ek Plumber (Service Provider) apna number aur kaam ki details Yellow Pages directory (Registry/UDDI) mein Publish karta hai. Aap (Client) us directory mein jakar plumber ko Find karte hain. Jab aapko number (WSDL) mil jata hai, tou aap direct plumber ko call kar ke apna kaam karwate hain (is direct communication ko Bind kehte hain, jo SOAP ke zariye hota hai).

3. Deep Dive: WSDL & UDDI

WSDL (Web Services Description Language)

WSDL is an XML file that describes the technical contract of the web service. It tells the client:

  • What operations/functions are available.
  • What parameters (data types) to send.
  • What data type the response will be.
  • The exact URL endpoint to send the SOAP message to.

UDDI (Universal Description, Discovery & Integration)

UDDI is a repository of web services on the internet. Machines or humans can search it to discover different web services. It provides standard APIs to publish and query services.

Important Exam Point: Remember the mapping!
Publish = Provider -> Registry
Find = Requestor -> Registry
Bind = Requestor -> Provider

Quick Revision - Lecture 45

  • Service Provider: Creates the service.
  • Service Requestor: Uses the service.
  • Service Registry (UDDI): Catalogs the service.
  • Publish, Find, Bind: The core lifecycle of Web Service architecture.
  • WSDL: The XML "instruction manual" for how to connect to the service.
